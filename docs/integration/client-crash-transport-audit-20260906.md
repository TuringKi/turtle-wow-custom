# 1.18.1 客户端出副本崩溃：运输路径对齐审计

## 结论与证据边界

发现并核实：已安装的数据文件来自用户提供的 `/root/Turtle1181bots.7z`，但正式世界库 12 条已启用船／飞艇模板的 `data0` 仍使用旧版 TaxiPath 编号。这是明确的数据库与 DBC 不一致，也是本次客户端崩溃的高度可疑原因；尚需同一客户端复测才能确认问题彻底消失。

用户日志时间为 2026-09-06 16:11:01，build 5875，EIP `0x00453885`。指令字节 `D9 04 B0` 为 `fld dword ptr [eax+esi*4]`，EAX=ESI=0，读取的是空指针指向的浮点数。公开的 5875 客户端逆向分析将 `0x453840` 定位为曲线路段定位、`0x454580` 定位为朝向计算；日志调用栈覆盖这些函数，并含运输物体 type 15 的虚表值 `0x80b798`。这些证据指向运输路径／朝向计算，而不是仅凭日志中的小地图贴图字符串判定贴图损坏。

来源：[曲线及路段计算](https://github.com/samwhosung/wow-1121-client-internals/blob/dca75dd7c6160f6bee7cee4c6c6cedaa189289cd/docs/math-primitives.md)、[运输物体更新](https://github.com/samwhosung/wow-1121-client-internals/blob/dca75dd7c6160f6bee7cee4c6c6cedaa189289cd/docs/object-model.md)。这是对公开 en-US 5875 分析的交叉印证，尚未取得用户实际修改版 WoW.exe 做逐字节比对；build 5875 本身不能区分 Turtle 内容补丁版本。

本轮重新从 7z 解出四个目录，逐文件做 SHA256 比较，不只依赖上次复制记录：

| 目录 | 压缩包文件数 | 安装文件数 | 压缩包文件缺失／内容差异 | 保留的旧版独有文件 |

| dbc | 158 | 158 | 0 / 0 | 0 |
| maps | 2,805 | 2,839 | 0 / 0 | 34 |
| vmaps | 6,923 | 6,957 | 0 / 0 | 34 |
| mmaps | 2,168 | 2,276 | 0 / 0 | 108 |

实际 DataDir 为 `/root/turtle-wow-custom/.install/bin/data`。核心读取的 44 个 DBC 文件头、记录长度及格式字段数匹配，包含由多段字符串定义格式的 Spell.dbc。3 个非核心读取 DBC 在压缩包中本来就是空文件，安装目录与之相同；其他非空 DBC 的文件长度也符合头部声明。

地图版本为 `MAPSz1.4`，vmap 为 `VMAP_6.0`，mmtile 的 magic/Detour/mmap 版本为 `0x4d4d4150 / 7 / 6`，与当前源码匹配。旧版独有文件没有删除，也没有证据证明它们是本次运输路径崩溃的来源。本检查证明服务器安装文件与指定压缩包一致，不证明用户客户端 MPQ 内的数据也一致。

新编号来自完整上游世界参考库；全部在安装版 TaxiPathNode.dbc 中具有连续节点、有效坐标、正确地图和至少两个停靠点。旧编号中 5 条没有节点，另外 7 条已经对应普通飞行路线，不能仅检查“编号存在”。此前启动日志跳过了 5 条活动航线，但其余错误航线仍可创建运输物体。

`Map::SendInitTransports` 在玩家进入地图时发送地图上的运输物体，不要求玩家靠近码头。因此从副本返回大陆可以触发这些对象的客户端更新；组队有机器人是已报告的复现条件，目前不能据此断定机器人本身就是直接原因。`HandleGameObjectQueryOpcode` 将模板的 24 个 data 字段发给客户端，data0 错误会传到客户端侧。

同时发现 `TransportMgr::GeneratePath` 的三个船只特例仍按旧路径编号 303、293、1500 判断。改为按船只模板 177233、176244、190550 判断，并给固定关键帧访问增加长度检查，以保留两条渡船的中途刷新及火花港船的靠岸朝向，不再受 DBC 路径重编号影响。

## 执行与复测

已在正式世界库执行 24：12 行 data0 更新，所有其他模板字段及非目标行的指纹保持一致；重复执行不再改变表。账号和角色数据库没有写入。逐条路径核对见 [transport-path-alignment.tsv](transport-path-alignment.tsv)。

代码增量编译通过，新程序已部署到 `.install/libexec/mangosd`，SHA256 为 `d8a22e4c2b13bf30a1a40bfffef44e1573c78b96a0e1c97704da12f908ddfd37`；旧程序备份为本机 `data-alignment/mangosd-before-transport-fix`。采用原子替换，没有中断正式服正在运行的旧进程，仍需用户重启。

SQL 修正后的隔离启动及关服退出码为 0；加入运输特例代码修正后，隔离启动仍成功到达 world ready，加载炉石 Lua，无缺列/缺表/数据库断言，12 条活动航线不再报告无效路径。未启用的 Naxxramas 模板 181056 的旧路径 436 警告仍保留，不属于 transports 中这 12 条活动航线。

后一次隔离关服退出码为 -11（SIGSEGV），与本轮改动前已经记录的偶发服务端关服问题相同阶段；因缺少有效崩溃栈，不能证明原因相同，也不能将其算作已修复。本轮证据支持运输数据不一致的修正，不支持“客户端或服务端所有崩溃均已解决”的结论。

执行前备份、文件指纹、路径节点及隔离校验记录保存在 `/root/turtle-wow-startup-check/data-alignment/`。正式服不用于测试；隔离环境只使用世界库副本与合成账号／角色库。

用户复测步骤：重启世界服加载新模板和程序；完全退出客户端后，将客户端 `WDB` 文件夹改名备份（不要改 Data 或 WTF），再启动客户端，以重新取得物件模板缓存。先用原队伍按原方式出副本，再比较不带机器人时的行为。若仍崩溃，保留新日志、准确副本和出本方式，并进一步比对客户端 MPQ 中的 TaxiPath/TaxiPathNode；服务器文件一致不能替代客户端侧校验。

客户端会把服务器返回的物件模板持久化为 WDB，参见 [DBCache](https://github.com/samwhosung/wow-1121-client-internals/blob/dca75dd7c6160f6bee7cee4c6c6cedaa189289cd/docs/dbcache.md)。不应以 `.reload eluna` 代替世界服重启或客户端缓存刷新。
